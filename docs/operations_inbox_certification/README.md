# Operations Inbox Certification Framework

Repeatable framework for certifying one incoming Operations Inbox request at
a time against the pipeline that already exists in
`services/operations_inbox_service.py`. It does not add Inbox functionality
- it only measures the functions already implemented.

## Files

```
tests/fixtures/operations_inbox/<CASE_ID>/
    case.yaml          required case metadata (see fields below)
    email.txt|.eml      the test email (email.eml if attachments must live inside the message)
    expected.json       hand-approved expected extraction/decision, defined BEFORE any code change
    attachments/        files merged into the message's attachment list (e.g. a booking PDF)
    actual.json         generated by the harness on every run - last captured actual result
    verification.md     lifecycle checklist + acceptance decision for this case

tests/integration/operations_inbox/
    harness.py                  fixture loading, scratch-DB safety gate, pipeline execution,
                                 actual-result capture, comparison/accuracy logic
    test_case_000_smoke.py      permanent regression test + copy-paste template for every real case

scripts/run_inbox_case.py       CLI: python scripts/run_inbox_case.py CASE-000
```

## Required database

Every run needs `INBOX_CERTIFICATION_DATABASE_URL` set to an empty,
disposable PostgreSQL database - same opt-in pattern as
`tests/test_migration_runner.py`'s `MIGRATION_TEST_DATABASE_URL`. The
harness:

- Refuses to run if the variable is unset (`MissingScratchDatabaseError`).
- Refuses to run if the URL can't be parsed, if the database name doesn't
  carry an unmistakable non-production marker (`dev`/`test`/`qa`/`sandbox`/
  `scratch`/`disposable`/`cert`/`certification`/`ci`), or if a separate
  `INBOX_CERTIFICATION_DATABASE_IDENTITY` env var isn't set to the exact
  sanitized `host[:port]/database` identity being targeted
  (`CertificationSafetyError`) - it never reads `.streamlit/secrets.toml`,
  the environment's `DATABASE_URL`, or any other application secret for
  this decision (see CTMS-010).
- Applies every migration (idempotent - safe to run against an
  already-migrated scratch DB) before each case.
- `TRUNCATE ... RESTART IDENTITY CASCADE`s every inbox/load-adjacent table
  before each case, so every run starts from a clean database state.

This repo already has a scratch Postgres container for this purpose
(`calitrans-postgres-scratch`, `localhost:5433`) with a dedicated
`calitrans_inbox_cert` database. Never point this at production.

## Running a case

```bash
export INBOX_CERTIFICATION_DATABASE_URL=postgresql://calitrans_test:calitrans_test_pw_2026@localhost:5433/calitrans_inbox_cert
export INBOX_CERTIFICATION_DATABASE_IDENTITY=localhost:5433/calitrans_inbox_cert
python scripts/run_inbox_case.py CASE-000
```

This: loads the fixture, resets the scratch database, runs the fixture
email through the real `sync_operations_email_engine` (the same function the
Streamlit sync button calls - only `email_client.fetch_operations_email_sync`
is replaced with the fixture message instead of a real IMAP fetch),
captures `actual.json`, compares it to `expected.json`, reprocesses the same
email once more without resetting data to check duplicate protection, and
prints every required measurement.

## Required measurements

Computed by `harness.compare()` for every run:

| Measurement | Meaning |
|---|---|
| classification_accuracy | `intent` field matches |
| service_flow_accuracy | `service_flow` field matches |
| critical_field_accuracy | % of `case.yaml`'s `critical_fields` that match |
| all_field_accuracy | % of every populated `expected.json` field that matches |
| container_count_accuracy | `container_count` matches |
| container_number_accuracy | `containers` list matches |
| existing_load_match_accuracy | `existing_load_match` matches |
| queue_resolution | PASS/FAIL on `queue` |
| duplicate_protection | PASS/FAIL - row count unchanged after reprocessing the same email |
| exact_record_pass | true only if zero field differences |

Thread accuracy isn't a single number in `compare()` - for multi-message
cases, check `_row_count`/`_row_ids` in `actual.json` against how many
distinct `order_intake` rows/conversation keys the case expects.

## Case lifecycle (hard rule)

A case may not be marked Passed unless, in order:

1. Fixture created
2. Expected result approved *before* any code change
3. Email imported
4. Processing executed
5. Actual result captured
6. Results compared
7. Any defect corrected
8. Permanent regression test added
9. Clean rerun passes
10. Duplicate rerun creates no duplicate records
11. Full existing suite still passes
12. Case accepted

## Adding a new case

1. Copy `tests/fixtures/operations_inbox/CASE-000/` to `CASE-0XX/`.
2. Write `case.yaml`, `email.txt`, `attachments/` for the real scenario.
3. Write `expected.json` **before** touching any pipeline code, from the
   business requirements - not from whatever the code currently outputs.
4. Run `python scripts/run_inbox_case.py CASE-0XX`, inspect the diff.
5. If the diff reveals a real defect, fix the implementation (not the
   fixture) and rerun.
6. Copy `test_case_000_smoke.py`, change `CASE_ID`, keep the three test
   functions (clean pass, duplicate rerun, cross-run determinism).
7. Run the targeted test 3x, then the full suite once.
8. Fill in `verification.md` and record the acceptance decision.

Do not begin the next case until the current one is ACCEPTED.
